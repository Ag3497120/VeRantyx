# Shared GPU intermediate layer

VXRuntime will use one API-neutral GPU layer for its in-tree Direct3D 11, Direct3D 12 and Vulkan implementations. Each API remains a real front end with its own externally visible behavior. The shared layer is the internal boundary between those front ends and Metal.

```text
D3D11 (COM, implicit state, DXBC) ─┐
D3D12 (COM, explicit state, DXIL) ─┼─> common GPU IR ─> Metal backend
Vulkan (dispatch handles, SPIR-V) ─┘
```

## Responsibilities

| Layer | Owns |
|---|---|
| API front end | Windows ABI and object lifetime; API validation and capability reporting; API-specific resource states, descriptor rules, synchronization and presentation behavior |
| Common GPU IR | Device capabilities; resource and view descriptions; normalized descriptor layouts, bindings and component mappings; pipeline descriptions; ordered render, compute, copy, clear, query and barrier operations; submission dependencies |
| Metal backend | Metal resource allocation and lifetime; pipeline creation/cache; command encoders and submission; Metal events, drawable acquisition and presentation |
| Shader front ends | DXBC, DXIL and SPIR-V decoding and validation, with stage and binding metadata |
| Shader backend | MSL generation from a shared typed shader representation when that representation covers the required semantics |

The common layer must preserve ordering and access information. D3D12 resource barriers and Vulkan image layouts/synchronization are interpreted by their front ends and lowered to explicit common resource accesses and dependencies. D3D11's implicit hazards and immediate-context ordering are tracked by its front end and expressed in that same form. A backend may optimize redundant transitions only after it has enough information to preserve the source API's observable behavior.

Shader built-ins retain API-neutral execution semantics alongside their original source values. `SubgroupSize` and `SubgroupLocalInvocationId` normalize DXIL `WaveGetLaneCount`/`WaveGetLaneIndex` (opcodes 112/111) and SPIR-V `BuiltIn` values 36/41. The compute MSL emitter maps them to `[[threads_per_simdgroup]]` and `[[thread_index_in_simdgroup]]`. DXIL `WaveActiveAnyTrue`/`WaveActiveAllTrue` (opcodes 113/114) and SPIR-V `OpGroupNonUniformAny`/`OpGroupNonUniformAll` normalize to subgroup-any/all arithmetic operations; MSL maps them to `simd_any`/`simd_all`, whose predicates cover active lanes. The DXIL common route is compute-only until pixel helper-lane participation can be represented and checked. This subset does not advertise the full D3D12 `WaveOps` or Vulkan subgroup feature sets, and Vulkan runtime pipeline support remains gated by its frontend. The DXIL definitions follow Microsoft's [`WaveActiveAnyTrue`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/waveanytrue) and [`WaveActiveAllTrue`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/wavealltrue); the SPIR-V execution-scope and capability rules follow Khronos's [`OpGroupNonUniformAny`](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html#OpGroupNonUniformAny) and [`OpGroupNonUniformAll`](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html#OpGroupNonUniformAll). Metal's matching active-thread semantics are in Apple's [Metal Shading Language specification](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf).

The common shader IR also represents 32-bit subgroup signed/unsigned minimum and maximum reductions. DXIL compute `WaveActiveMin`/`WaveActiveMax` (`dx.op.waveActiveOp.i32`, selectors 2/3 and `SignedOpKind` 0/1) and SPIR-V `OpGroupNonUniformSMin`, `UMin`, `SMax` and `UMax` lower to the same operations. The SPIR-V frontend requires `GroupNonUniform` plus `GroupNonUniformArithmetic`, `Subgroup` scope and the `Reduce` group operation. MSL uses `simd_min`/`simd_max`; DXIL's signless `i32` values are bitcast through signed `int` for signed reductions. Focused DXIL and SPIR-V tests cover all four variants, and the generated compute MSL compiles with Apple's Metal compiler. This is a translator/compiler check only: D3D12 `WaveOps` and Vulkan subgroup features remain unadvertised, and the Vulkan frontend does not submit these shaders through the common path. The mappings follow Microsoft's [DXIL wave-op definitions](https://github.com/microsoft/DirectXShaderCompiler/blob/main/include/dxc/DXIL/DxilConstants.h), [HLSL `WaveActiveMin`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/waveactivemin) and [HLSL `WaveActiveMax`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/waveactivemax), Khronos's [SPIR-V subgroup reductions](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html#Group_Non-Uniform), and Apple's [Metal Shading Language specification](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf).

The shared arithmetic IR also carries 32-bit integer subgroup product and bitwise AND/OR/XOR reductions. The SPIR-V reader accepts `OpGroupNonUniformIMul`, `OpGroupNonUniformBitwiseAnd`, `OpGroupNonUniformBitwiseOr` and `OpGroupNonUniformBitwiseXor` alongside the min/max operations above, subject to `GroupNonUniform` and `GroupNonUniformArithmetic`, `Subgroup` execution scope and `Reduce`. The DXIL reader maps compute `WaveActiveBitAnd`, `WaveActiveBitOr` and `WaveActiveBitXor` (dx.op 120, operation kinds 0/1/2) into the same bitwise operations. MSL emits `simd_product`, `simd_and`, `simd_or` and `simd_xor`; the product mapping is currently SPIR-V-only. Synthetic tests cover each IR operation and reject unsupported SPIR-V scopes/capabilities. The DXIL subgroup fixture is compiled by Apple's Metal compiler as part of `make check`. These translator/compiler tests do not exercise subgroup execution on a GPU, and neither API frontend advertises its full subgroup feature set. This follows the Khronos [SPIR-V group-non-uniform instruction rules](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html#Group-Non-Uniform), Microsoft's [DXIL wave-op definitions](https://github.com/microsoft/DirectXShaderCompiler/blob/main/include/dxc/DXIL/DxilConstants.h) and HLSL [`WaveActiveBitAnd`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/waveactivebitand), and Apple's [Metal Shading Language specification](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf).

Descriptor sets, D3D12 root signatures/heaps and D3D11 register slots have different API rules. Their front ends validate those rules and lower the resulting bindings into a normalized layout; they do not expose D3D or Vulkan handles to the backend. A binding namespace preserves separate D3D12 SRV, UAV, CBV and sampler register files, while Vulkan uses namespace zero. Repeated register keys are retained only when their shader-stage visibility masks do not overlap. Vulkan's single binding per set/binding remains a single record with its declared stage mask. Immutable descriptor snapshots retain an API-neutral four-channel image mapping (identity, source channel, zero or one). The common Metal executor and D3D12 common-compute binder apply that mapping with a Metal texture view, which changes texel reads and samples while preserving writes. Ordinary Vulkan GPU tests cover sampled `OpImageFetch` and storage-image `OpImageRead`; the D3D12 compute binder uses the same mapping representation. Capabilities are reported from the common backend's real support, with front ends translating those capabilities into each API's feature queries. Unsupported behavior must remain unsupported rather than being advertised optimistically.

Presentation follows the same boundary: DXGI and Vulkan WSI keep their surface and swap-chain contracts, while both use a common Metal drawable/present path where their lifetimes permit it.

The common stream includes repeated 1-, 2-, 4-, 8-, and 16-byte buffer patterns alongside buffer updates and copies. Vulkan checks `vkCmdFillBuffer` usage, four-byte alignment and range rules in its front end, then records a 32-bit fill. D3D11 typed, raw and structured buffer UAV clears retain their own format, stride and element-range rules, then record the corresponding common pattern fill. D3D12 raw-buffer clears, typed `R`, `RG` and `RGBA` 8-, 16- and 32-bit integer buffer clears, and packed `R10G10B10A2_UINT` buffer clears also preserve their descriptor ranges and record common pattern fills; other typed formats and texture views keep the D3D12-specific clear path. Metal stages a bounded repeated pattern and encodes ordered blit copies; narrow subranges that Metal cannot copy with its alignment rules use a synchronous shared-memory write in the reusable submission backend.

Color and depth/stencil clears now use common commands. The stream retains the selected texture and snapshots signed, half-open pixel rectangles; an empty list means the whole selected attachment. The reusable `gpu_ir_metal` submission backend executes full clears as render-pass load actions and rectangular clears with scissored raster work. D3D12 preserves its RTV/DSV and resource-state validation in the front end, then uses the same Metal clear encoders inside command-list replay. Vulkan `vkCmdClearColorImage` records typed full-image and array-layer-range clears for supported transfer images, and the initial Vulkan render-pass path records its load/clear/store and render-area commands through the common stream. Vulkan depth/stencil clears and broader draw state remain future work.

The common stream also has begin/end render-pass commands for one single-sample color attachment and a signed half-open render area. It retains Vulkan 1.0 load/store actions and typed clear values. The Metal backend performs clears with a scissored typed clear pass so pixels outside Vulkan's render area remain intact; it preserves concrete values for `DONT_CARE`, which is permitted because Vulkan leaves those in-area contents undefined. `vkCmdBeginRenderPass` and `vkCmdEndRenderPass` record these common commands, so ordinary Vulkan clear/readback tests pass through the Metal render-pass backend. The Metal backend compiles graphics pipelines and executes point, line and triangle draws with either sequential vertices or retained uint16/uint32 index buffers; each common draw can carry an API-neutral viewport/scissor pair, and the backend clips scissor state to the active render area. Common pipeline records describe up to 16 vertex bindings, 32 attributes, and up to 8 color-blend attachments. Each blend attachment retains enable, source/destination factors, color/alpha operations, and channel write mask; pipeline state also retains four blend constants and alpha-to-coverage. D3D11 normalizes its eight render-target blend descriptors, and D3D12 normalizes the attachments in its graphics PSO; both snapshot dynamic blend constants on each recorded draw, including D3D12 indirect draws. The Metal backend applies a draw snapshot when present, otherwise the pipeline constants. Vulkan currently supplies one attachment and supports the implemented fixed-factor/operation subset with static pipeline constants or `VK_DYNAMIC_STATE_BLEND_CONSTANTS`; `vkCmdSetBlendConstants` values are snapshotted on direct and indirect draws, and missing values are rejected when an enabled blend equation uses a constant factor. Vulkan logic operations, multiple color attachments, and alpha-to-coverage in the single-sample path remain unsupported. Common pipeline records also describe vertex input; Float32 formats retain their shared component format while D3D11 and D3D12 can retain a frontend-native format's byte width and leave its numeric conversion rules in the API-specific pipeline. Draw snapshots retain bound buffers, offsets, byte ranges and dynamic strides. Recording checks required bindings and the complete fetch range for statically known nonindexed vertex and instance IDs; indexed and indirect draws check their buffer/argument ranges and minimum attribute extent because their actual vertex IDs or counts are GPU data. Metal maps these streams to buffer indices 14–29, immediately below its runtime-data slot 30. Vulkan's static pipeline values and dynamic `vkCmdSetViewport`/`vkCmdSetScissor` state both feed this draw state. The SPIR-V reader normalizes common `Position`, `VertexIndex`, `InstanceIndex`, `FragCoord`, `FrontFacing` and `FragDepth` built-ins, retains user I/O locations and component/index decorations, and preserves interpolation qualifiers in typed shader IR. The MSL emitter links matching smooth float32 scalar/vector varyings through `[[user(locnN)]]` fields in vertex-output and fragment-stage input structures. Vulkan validates fragment inputs against vertex outputs, creates the Metal pipeline, records `vkCmdDraw` and `vkCmdDrawIndexed` through common GPU IR, and reads clipped red pixels back from an RGBA8 attachment. Flat, no-perspective, centroid, sample and invariant qualifiers are explicitly rejected until their MSL semantics are implemented. Vulkan's current vertex-format subset, depth/stencil attachments, and multiple color attachments remain limited as documented in `Vulkan-SPIR-V.md`.

The shared MSL emitter now has layout-aware vertex and fragment entry points. The fragment path maps combined image-samplers and separate sampled-image/sampler bindings to Metal texture and sampler arguments and lowers supported explicit-LOD and fragment implicit-LOD samples into common shader IR. The implicit path materializes coordinate derivatives before descriptor-index guards and emits Metal `gradient2d` sampling. CPU-only SPIR-V fixtures check reflected layouts, slots, and derivative expressions; Metal compilation covers both descriptor forms. Vulkan graphics pipeline creation validates and snapshots fragment descriptors, and the Metal render encoder binds each draw's snapshot. The ordinary integration test uploads a known texel, records and submits combined and separate descriptor draws for both LOD forms, reads the attachment back, and checks the sampled pixels and untouched clear pixels.

The DXIL adapter now lowers narrow graphics-I/O forms. A fragment shader may read scalar components from a metadata-described float32 `SV_Position` element (the non-geometry vertex-axis operand is `undef`), load scalar bool `SV_IsFrontFace` as the common `FrontFacing` builtin, and write all four float32 components of one metadata-described `SV_Target0` element, in one basic block. The front-facing input must be the `I1` component type, `IsFrontFace` semantic kind, one row and one column; its signature start row may be zero or the `-1` system-generated sentinel used by newer shader models, and its start column must be zero. The common MSL emitter supplies Metal's `[[front_facing]]` bool. The color output is represented as one location-0 `float4`. A vertex shader may read scalar components from metadata-described generic float32 input signatures with one row and one to four columns, then write all four float32 components of one `SV_Position` element in one basic block. Signature IDs map to attribute locations using the DXIL input-signature order; the common vertex MSL emitter represents the position output as `[[position]]` and inputs as `[[attribute(n)]]`. Synthetic DXIL tests check signature mapping, channel coverage, common IR and generated MSL, and Metal compiles the generated stage function; partial output writes remain unsupported. D3D12 selects common fragment lowering only for one render target, the default sample mask and no fragment resource bindings. It selects common vertex lowering when all generic inputs used by the common shader are matched to input-layout attributes and the vertex shader has no resource bindings; unsupported signatures and unmapped layouts keep the direct DXIL-to-MSL path. The common pipeline record now permits graphics front ends to retain only the stages they lowered, while the D3D12 front end validates the full native pipeline and its remaining stages. Multiple/partial render targets, other vertex outputs, other system-value inputs and non-float32 values remain outside this slice. These mappings follow Microsoft's [DXIL signature metadata](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#signature-record-metadata), [`loadInput`](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#accessing-signature-value-in-operations) and scalar [`storeOutput`](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#accessing-signature-value-in-operations) definitions.

`GPU_IR_SHADER_OP_DISCARD` represents a scalar conditional fragment discard. The DXIL adapter validates `dx.op.discard` opcode 82 and lowers its boolean condition; the shared MSL emitter writes `discard_fragment()`. `GPU_IR_SHADER_OP_TERMINATE_INVOCATION` separately represents SPIR-V `OpKill`, which is an unconditional fragment terminator and must end its block. The single-block fragment MSL path emits `discard_fragment()` and a typed return for that terminator. CPU tests cover DXIL lowering, SPIR-V reading/lowering, and MSL emission; generated MSL is compiled by the normal check target. D3D12 uses common DXIL fragment MSL only for the narrow `SV_Target0` output path described above; its vertex stage and unsupported fragment shaders remain on direct DXIL-to-MSL. SPIR-V `OpTerminateInvocation` remains unsupported until its version/extension and Vulkan feature requirements are validated. These mappings follow Microsoft's [DXIL Discard contract](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#discard), Khronos's [SPIR-V `OpKill` definition](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html#OpKill), and Apple's [Metal Shading Language specification](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf).

The common pipeline metadata now records vertex attribute component count, byte width, and float/signed/unsigned conversion class for 32-bit values, 16-bit float/integer values, and 8/16-bit normalized integer values. Vulkan lowers supported `VkFormat` values into these records, while D3D11 and D3D12 can keep frontend-native formats and their own interpretation. The Metal backend maps these common formats to `MTLVertexFormat`; the ordinary Metal raster test exercises 8-bit UNORM to float input and checks the rendered pixels. Scaled, sRGB, packed, and 64-bit Vulkan vertex formats remain unsupported.

D3D12 direct and indexed draw records snapshot bound buffer resources, GPU-address-relative offsets, index format and per-view stride in the common command. The D3D12 front end lowers input-slot classification, instance step rate and attribute byte widths while retaining semantic-to-attribute mapping in API-specific pipeline state. Ordinary command-list `ExecuteIndirect` draw records snapshot the IA views too; bundle draws use inherited IA state as required by the bundle contract. D3D11 immediate draws and Vulkan direct/indirect draws also provide their bound vertex ranges to the common validator.

Vertex and index buffer bindings also retain their API-bound byte ranges. Common recording checks each captured range against its backing resource, and direct indexed draws check `firstIndex` and `indexCount` against the bound index range. For nonindexed direct draws it checks the last per-vertex and per-instance attribute fetch against the view, applying the binding's stride and instance step rate. Indexed vertex IDs and indirect draw counts are read by the GPU, so their actual vertex fetch bounds cannot be proven during command recording. Vulkan captures the bytes remaining in each `VkBuffer` from its bound offset; D3D11 captures its bound byte offsets; D3D12 captures the `SizeInBytes` from its VBV and IBV.

## Migration stages

1. Define API-neutral resource, view, format, descriptor-layout, pipeline and command records. Keep API handles and validation in their existing front ends. Implemented slices are reference-counted buffer/texture resources, reference-counted typed/structured/raw buffer views with range and access validation, immutable descriptor and push-constant layouts, retained sparse descriptor-state snapshots with primary and optional auxiliary resource accesses and ordered bind commands, retained graphics/compute pipeline records, direct and indirect compute dispatch including fixed-stride ranges with optional count buffers, indexed/non-indexed draw recording, whole-resource stage/access annotations on draw and dispatch commands, ordered buffer/full-resource/texture-region copies, multisample resolves, attachment clears and resource barriers.
2. Lower the remaining D3D12 command-list operations and submission to the common records, then move their execution behind the Metal backend. Ordinary compute dispatches and draw calls now use common pipeline/operation records; D3D12 resource, descriptor, root-argument, attachment and queue validation remains in `d3d12.m`.
3. Move the remaining D3D11 resource and descriptor binding references onto the same resource and command interfaces. Keep its immediate-context semantics, render-pass decisions and cross-process IOSurface behavior in the D3D11/DXGI front ends.
4. Expand the Vulkan front end, which now has dispatchable/non-dispatchable handles, basic feature queries, uniform/storage-buffer and sampled/storage-image/sampler descriptor sets, push constants, buffer/image transfers, optimal RGBA8 storage/sampled images, image views, sampler-backed compute sampling, compute dispatch, `vkCmdClearColorImage`, scoped buffer/image synchronization, one-color render passes, and a builtin-shader graphics pipeline/draw path with smooth float32 varyings. Add vertex input, WSI and broader Vulkan synchronization.
5. Keep the existing DXBC→MSL and DXIL→MSL paths while the API IR stabilizes. The owned typed shader IR, first SPIR-V lowering slice, narrow compute and initial graphics MSL emitters, and initial DXIL-to-common-IR adapter now exist. D3D12 direct compute dispatches use a common-IR MSL pipeline when both DXIL lowering and Metal pipeline creation support the shader; unsupported shaders and indirect dispatch retain the direct DXIL-to-MSL path. Expand the shared shader subset and DXIL adapter operation by operation, then add a DXBC adapter and broaden Vulkan's SPIR-V/common-IR integration without bypassing front-end validation.

This stages shader unification separately from API command/resource unification. D3D11 `CopyResource` and `CopySubresourceRegion` buffer/texture copies now lower through the common records, alongside D3D12 copies, resolves and barriers. D3D11's ordinary immediate-context draw and compute dispatch calls now execute through common GPU IR commands; the front end still owns its bound state, geometry-shader and stream-output paths, and descriptor binding. D3D12 compute and graphics PSO creation now creates retained common pipeline records. Ordinary D3D12 `Dispatch`, `DrawInstanced` and `DrawIndexedInstanced` calls execute through common operations. `ExecuteIndirect` signature decoding and argument-driven D3D12 state changes remain in its front end; fixed-signature `DISPATCH` and draw operations use common indirect operations, including retained optional count buffers, while expanded fallback draw/dispatch commands use transient common operations. The typed `R32_SINT`, `R32_UINT` and `R32_FLOAT` buffer compute subsets lower through common DXIL shader IR and common MSL on D3D12 direct dispatch. Runtime GPU tests cover each format, including `FirstElement`, `GetDimensions`, signed and floating arithmetic, and readback. The descriptor table is snapshotted from the current root binding and encoded into dense Metal buffer slots. Other supported-by-direct-translation shaders keep the direct DXIL MSL pipeline when common lowering or compilation does not support them, and indirect dispatch still uses that direct pipeline. The Vulkan compute and initial graphics front ends create immutable descriptor/pipeline records and record dispatch/draw work through common GPU IR. During D3D11 draws and dispatches, reflected CBV/SRV/UAV/sampler bindings are resolved into temporary common descriptor snapshots for resource-access annotation. Buffer SRV/UAV entries also carry typed, structured or raw element ranges when the view and resource metadata identify them; MSL argument encoding still uses D3D11 state. During D3D12 replay, finite reflected root-table/root-descriptor bindings and static/table samplers are resolved into a temporary common descriptor snapshot for resource-access annotation; hidden UAV counters are carried as auxiliary buffer accesses. The common DXIL path binds the subset it supports from that snapshot; remaining MSL argument encoding and direct `ResourceDescriptorHeap` indexing use D3D12-specific state. The remaining migration must preserve each front end's own validation and ordering rules.

Draw and compute commands can retain conservative whole-resource access annotations with shader stage and access masks, and the common layer validates the resource kind and pipeline-stage compatibility. D3D12 replay resolves reflected root descriptors and descriptor tables against the currently bound command-list state, then annotates shader resources, vertex/index buffers and render attachments. Direct `ResourceDescriptorHeap` indexing conservatively checks and annotates live entries whose SRV, UAV or CBV class is used by the shader; this may include entries the dynamic index does not select. The Metal D3D12 callbacks pass those annotations to `useResource` with the corresponding read/write usage and render stage. D3D11 ordinary draws and compute dispatches resolve DXBC resource masks and bound CBV/SRV/UAV/sampler values into a temporary common descriptor snapshot, then derive accesses for bound shader resources, vertex/index buffers and attachments and pass them through common commands to Metal `useResource`. Its geometry-shader and stream-output paths still use API-specific command execution. The existing all-resource residency fallback remains in place, and resource annotations do not yet drive barrier elimination or hazard inference.

## Current implementation boundary

The DXIL-to-common-IR adapter supports one bounded fragment-I/O combination: scalar `loadInput` reads from metadata-described float32 `SV_Position` (`row=0`, columns 0–3, geometry-axis operand `undef`) and scalar bool `SV_IsFrontFace` (`I1`, semantic kind `IsFrontFace`), plus complete RGBA float32 `storeOutput` writes to `SV_Target0`, all in one basic block. The common MSL emitter maps these inputs to fragment `[[position]]` and `[[front_facing]]` builtins and compiles the fixture. Other DXIL input semantics, partial or multi-target outputs, nonzero rows, resource-backed fragment shaders and multi-block graphics shaders remain on the direct DXIL-to-MSL path or unsupported by common IR. Microsoft's [DXIL signature metadata](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#signature-record-metadata) specifies the semantic kind and I1 component type; its [operation specification](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#accessing-signature-value-in-operations) defines `LoadInput` as a scalar operation with row/column offsets relative to the signature element and requires the vertex-index operand to be `undef` outside geometry/domain shader use. Microsoft documents `SV_IsFrontFace` as a bool pixel-shader input in its [HLSL semantic reference](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-semantics).

The D3D11 translator in `dxbc.c` emits MSL directly. The D3D12 reader in `dxil.c` and translator in `dxil_msl.c` are also in-tree and emit MSL without LLVM. The common GPU IR in `gpu_ir.h`/`gpu_ir.c` handles retained buffer and texture references; typed, structured and raw buffer-view ranges and lifetime; immutable descriptor layouts keyed by set, namespace and binding with descriptor kinds, array counts, stage visibility and access masks; optional auxiliary buffer accesses attached to descriptor snapshots; push-constant ranges; retained graphics/compute pipeline records, direct and indirect compute-dispatch commands including fixed-stride ranges with optional retained count buffers and offsets, direct indexed/non-indexed draws with up to 16 retained vertex-buffer bindings, and fixed-stride indirect draw commands with optional retained count buffers and offsets; D3D11 full-resource and buffer/texture-region copies; D3D12 buffer/full-resource/texture-region copies; multisample resolves with explicit source/destination rectangles; ordered transition/UAV/aliasing/global barriers; and scoped memory, buffer and image dependencies. D3D12 typed buffer SRV/UAV descriptors now create Metal texture-buffer views through the common view object. The view's normalized base range and element count feed descriptor construction, and DXIL MSL applies `FirstElement` and `NumElements` to typed loads, stores and `GetDimensions`. Raw and structured buffers remain byte-addressed. The layout validator permits repeated binding keys only when their stage masks are disjoint, descriptor/access compatibility, shader-stage masks, push-constant alignment and stage-overlap rules. D3D12 root-signature creation now builds a normalized layout record for descriptor tables, root descriptors and static samplers. The front end still keeps its native root-signature records for descriptor-table offsets, root-constant registers and command-list binding; root constants are not misrepresented as Vulkan-style byte ranges. `spirv_ir.c` maps SPIR-V descriptor declarations and supported push-constant blocks into common layouts for a selected entry point. The Vulkan compute front end uses those common records for uniform/storage-buffer, sampled/storage-image and sampler descriptor sets, push constants and dispatch; fixed descriptor arrays now include feature-gated dynamically uniform indexing for sampled images, samplers and combined image-samplers. During D3D12 replay, reflected root tables/root descriptors and static/table samplers are captured in temporary common descriptor-state snapshots used to derive common resource-access annotations, while the actual D3D12 root argument encoding remains in the API front end. D3D11 descriptor binding remains API-specific. Texture metadata carries block dimensions and bytes per block, so the common copy validator handles BC block alignment and the Metal backend uploads and reads back BC data with block-row pitches. D3D12 validates resolve format families, dimensions, sample counts and subresources, and validates barrier kinds, flags, state masks, resource flags, resolve sample counts and subresource bounds before recording. Its front end carries each resource's creation state and sparse per-subresource overrides, checks transition before-states and split-barrier pairing in serialized queue submission order, validates copy and resolve states, and requires ExecuteIndirect argument/count buffers to be readable in `INDIRECT_ARGUMENT`. COMMON-state use follows the D3D12 promotion table for buffers and eligible textures; promoted read states can merge, and eligible resources decay at the end of an `ExecuteCommandLists` call, never between lists in that call. UPLOAD and READBACK buffers retain their creation, access and barrier restrictions while following buffer decay at submission boundaries. Command operations are checked against Direct, Compute, Copy, and command-list capabilities. Direct lists snapshot a restricted graphics bundle subset at ExecuteBundle recording time; bundle draws inherit target/root state, and PSO, topology, root bindings and IA bindings changed by the bundle flow back to the parent. Descriptor heaps set by a bundle must match the parent heaps, and bundles cannot be submitted directly. The supported ExecuteIndirect bundle form is one Draw or DrawIndexed operation with no count buffer or root/IA updates. It also maps RTV/DSV descriptors back to their resource and view subresource, checks clear and draw attachment states (including read-only depth/stencil flags), checks bound vertex/index buffer states, and validates reflected finite CBV/SRV/UAV descriptor bindings at draw/dispatch against their required D3D12 states. Root-signature parsing rejects unknown root flags and invalid v1.1 descriptor-range/root-descriptor volatility flag combinations; SM 6.6 direct heap use requires the matching root-signature opt-in at PSO creation, and submission requires the corresponding shader-visible heap of the correct heap type to be bound. Submission checks every live descriptor in each direct resource-heap class used by DXIL against the required D3D12 state; access annotations carry matching CBV/SRV/UAV access masks. This conservative check can include entries a dynamic index never selects. A per-list update is transactional so a rejected list cannot partially advance tracked states. GPU-only root/IA-updating ExecuteIndirect inputs are per-record validated during preflight when the current list has no preceding GPU work; GPU-produced records later in that same list are staged after the producer prefix and passed through whole-list per-record state validation before expansion, with invalid records skipped; cross-queue ownership/fence semantics, other queue-type restrictions, partial D24S8/D32S8 and stencil-plane/decompress resolves, and Vulkan synchronization remain unvalidated. Metal resolves supported full color average subresources with a render-pass resolve; partial color average resolves use a cached Metal shader that averages all samples over the selected source rectangle and writes only the destination rectangle for normalized and floating-point formats. Color MIN/MAX resolves use typed Metal fragment pipelines for the supported normalized/floating-point and integer format set, including full subresources and partial rectangles; a varying-sample RGBA8 array test checks reduction results and preserves pixels outside the destination region; an RGBA8_UINT test compiles and executes the typed integer pipeline for partial MIN/MAX and full MAX. Metal replay closes active encoders at barriers so Metal's tracked-resource hazard handling orders those encoders. Texture copies with formats that do not map to a Metal texture still use the existing D3D12 replay path or remain unsupported by the backend. The common shader IR represents 32-bit integer atomics. The SPIR-V frontend lowers `OpAtomicLoad`/`OpAtomicStore`, `OpAtomicExchange`, `OpAtomicIAdd`, `OpAtomicISub`, `OpAtomicIIncrement`/`IDecrement`, `OpAtomicSMin`/`UMin`, `OpAtomicSMax`/`UMax`, `OpAtomicAnd`/`Or`/`Xor`, and `OpAtomicCompareExchange` for 32-bit integer StorageBuffer elements with Device scope and Relaxed, Acquire, Release, or AcquireRelease ordering when the required `UniformMemory` semantics bit is set. MSL emits relaxed atomic operations with device-scope sequentially consistent fences before releases and after acquires to preserve the requested ordering while using a stronger fence. Atomic store and read-modify-write operations require writable storage; atomic load accepts read-only storage and returns the loaded value, while atomic store has no result. Increment/decrement preserve the SPIR-V old-value result and use atomic fetch-add/sub by one. Compare-exchange retains separate Equal and Unequal memory-semantics operands in common IR; failure ordering accepts Relaxed or Acquire and cannot be stronger than success; MSL retries its weak primitive on spurious failure to preserve strong compare-exchange behavior. The DXIL frontend lowers the nine `AtomicBinOp` operations—Add, And, Or, Xor, signed and unsigned Min/Max, and Exchange—and `AtomicCompareExchange` for a single typed R32_SINT or R32_UINT buffer UAV. Both DXIL forms preserve the returned old value and emit device-scope relaxed MSL atomics behind the descriptor-range guard. The synthesized DXIL-to-common-IR Metal test runs each operation with 64 contending invocations and verifies readback; the Add case chains the first atomic's old value into a second atomic, and the compare-exchange case checks success, mismatch and old-value propagation under contention. Vulkan runtime fixtures check 64-way AcquireRelease/Acquire compare-exchange, 63-way AcquireRelease contention for each added read-modify-write operation, and Acquire load/Release store through common IR. `make check` compiles the generated MSL fixtures. The DXIL fixture tests the shared shader path; it is not a D3D12 command-list integration test. Other resource shapes, widths, storage classes and scopes, SequentiallyConsistent ordering and additional memory-semantics bits remain unsupported, as do SPIR-V atomic flag operations and DXBC-to-common-IR atomics. This follows Khronos [SPIR-V atomic load](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html#OpAtomicLoad), [atomic store](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html#OpAtomicStore), and [atomic RMW semantics](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html#OpAtomicIAdd), [OpAtomicExchange](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html#OpAtomicExchange), and [OpAtomicCompareExchange](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html#OpAtomicCompareExchange), Microsoft's [DXIL AtomicBinOp contract](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#atomicbinop), [DXIL AtomicCompareExchange contract](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#atomiccompareexchange), and [HLSL Interlocked operation semantics](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/interlockedmin).

## DXIL shader verification

`tests/shaders12/samplegrad_ps.hlsl` covers `SampleGrad` for 1D and 1D-array, 2D and 2D-array, 3D, cube and cube-array textures. The translator uses the active gradient components for each texture dimension and omits the array layer from the gradient, then Metal compiles the generated MSL as part of `dxil2msl`. It also covers the optional minimum-LOD clamp. Metal 1D texture sampling has no explicit LOD option, so the 1D cases use Metal's implicit sampling gradients; explicit 1D gradients and their clamp cannot be preserved on this backend.

DXIL `DerivCoarseX/Y` (83–84) read a single pair in each 2×2 stamp with Metal `quad_shuffle`, then broadcast that pair's difference by computing it in every lane. The selected pair is the top row for X and left column for Y; DXIL permits the implementation to choose either pair. `DerivFineX/Y` (85–86) use `quad_shuffle_xor` to fetch the horizontal or vertical neighbor, then choose the signed difference from the current SIMD lane's quad position. Fine derivatives are currently accepted only in pixel shaders. The translator fixture rewrites the checked-in `samplegrad_ps.dxil` module's explicit gradient samples as implicit samples to isolate the derivative operations, changes one coarse derivative of each axis to its fine opcode, checks that both lowering forms appear, and compiles the emitted MSL. This verifies translation and Metal compilation, not raster output on the GPU.

The DXIL-to-common-IR adapter lowers compute-stage `dx.op.barrier` (opcode 80) modes into common control-barrier and memory-barrier operations. DXIL `extractelement`/`insertelement` and SPIR-V `OpVectorExtractDynamic`/`OpVectorInsertDynamic` lower to typed Metal vector indexing for 32-bit integer indices; static DXIL `extractvalue`/`insertvalue` and SPIR-V `OpCompositeExtract`/`OpCompositeInsert` support one vector-lane index. Insertions copy the source vector before replacing the selected lane. Dynamic extraction and insertion keep the source-language out-of-range behavior (undefined or poison); the emitter does not clamp indices. It also lowers typed `R32_SINT`, `R32_UINT` and `R32_FLOAT` buffer SRV/UAV `BufferLoad`, `BufferStore`, and field-zero `GetDimensions`, including statically indexed single-descriptor `CreateHandle`. Float loads and stores use 32-bit bitcasts around the common byte-addressed `uint` buffer access, preserving the element bits while leaving range checks in bytes. Signed and unsigned integer views share the byte-addressed `uint` storage representation; DXIL's signed division, remainder, arithmetic right shift, comparisons, and scalar/vector `fptosi` and `sitofp` retain the operation's signed semantics in common IR, and MSL reinterprets 32-bit integers with `as_type` where needed. Scalar numeric `null` constants lower to zero, including zero indices emitted by DXC. LLVM fast-math instruction flags are retained as a common shader hint; the MSL backend emits the regular arithmetic expression. The adapter checks resource metadata, handle class, formats, offsets, masks and aggregate fields; unsupported buffer shapes, descriptor indexing, and operations still return `GPU_IR_UNSUPPORTED`. SRVs are represented as read-only resources and emit `device const uint*`; UAVs emit writable pointers. The common MSL path maps D3D12 SRV/UAV namespaces through the root-signature layout, snapshots the currently bound descriptor table, and executes direct compute dispatches on the same Metal device as the D3D12 backend. The ordinary `typed_buffer_cs.dxil` D3D12 runtime test covers nonzero `FirstElement`, `NumElements`, `GetDimensions`, dispatch and readback for `R32_UINT`. `typed_sint_buffer_cs.dxil`, compiled from `Buffer<int>` by the in-tree DXC runner, executes a negative `-40 / 2` through common DXIL IR and MSL with `R32_SINT` SRV/UAV views; readback verifies `-20`. Its adapter test confirms the signed divide flag and compiles the generated MSL. `signed_conversion_cs.dxil` runs through the common-IR D3D12 path: `-8` is converted with `sitofp`, multiplied and offset, then converted with `fptosi`; readback verifies the float bits `0xc1000000` and integer bits `0xfffffff5`. `typed_float_buffer_cs.dxil` exercises real `R32_FLOAT` SRV/UAV loads and stores, `FirstElement`, `GetDimensions`, unsigned-to-float conversion, arithmetic, common MSL compilation, D3D12 dispatch and readback (`3.5` produces `5.75`). Indirect dispatch and shaders outside the common subset continue through direct DXIL-to-MSL.

DXIL `Texture2D<float4>.GetDimensions` lowers a single non-arrayed float 2D SRV's width and height at a 32-bit mip level through common image-query IR; its returned mip count remains a separate query. The MSL emitter passes the selected level to Metal's texture dimension query. The DXC-compiled D3D12 runtime fixture checks mip 0 on a 7×5 texture with three mips, and the adapter compiles a second MSL fixture for mip 1. SPIR-V tests compile both dynamic `GlobalInvocationId.x` and LOD 1 through the same query operation. Texture2DArray also lowers the array-size field of its GetDimensions result to the common image-array-size query and Metal get_array_size(). The adapter test changes the resource kind and selected aggregate field in the existing DXIL fixture, then compiles the emitted MSL; this is synthetic adapter coverage, not a D3D12 array-resource runtime test. `Texture2DMS<float>.GetDimensions` also lowers its width, height and sample count through the same common IR; a DXC-compiled 7×5, 4x-MSAA D3D12 fixture reads back all three values through the runtime path. The mapping follows Microsoft’s [Texture2DMS `GetDimensions` reference](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-texture2dms-getdimensions) and Apple’s [`MTLTexture.sampleCount` property](https://developer.apple.com/documentation/metal/mtltexture/samplecount). Other resource formats remain outside this common slice. The mapping follows Microsoft's [DXIL operation specification](https://github.com/Microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#operations-via-external-functions) and HLSL [`GetDimensions` reference](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-to-getdimensions).

The DXIL adapter lowers `Texture2D<uint>.Load` and `Texture2DArray<uint>.Load` (opcode 66) for `R32_UINT` SRVs, `Texture2D<int>.Load` and `Texture2DArray<int>.Load` for `R32_SINT` SRVs, and scalar `Texture2D<float>.Load` for `R32_FLOAT` SRVs through a common mip-read operation. It accepts scalar result fields 0–3, signed 32-bit mip/coordinates; each field selects its matching MSL .x/.y/.z/.w component. DXIL's static offsets are in `[-8, 7]`; for array images it also consumes the signed 32-bit layer coordinate. Signedness comes from DXIL resource metadata because LLVM i32 is signless; when the DXIL result is signless but the MSL texture component is `int`, the emitter uses `as_type<uint>` to preserve the original 32-bit pattern. The float path keeps the image read as `float` and uses a bitcast only when the fixture stores the result bits into its integer UAV. The MSL emitter checks mip, coordinates and array-layer bounds using signed wide intermediates and returns a zero component when the load is out of range, matching the documented HLSL `Load` behavior. A separate common MSAA image-read operation covers scalar `Texture2DMS<float>.Load(int2, sampleIndex)` and `Texture2DMSArray<float>.Load(int3, sampleIndex)` on float32 multisampled SRVs. It checks signed 2D coordinates and, for arrays, the signed layer against `get_array_size()`, returns zero out of range, and forwards the sample index to `texture2d_ms::read` or `texture2d_ms_array::read`. The sample index remains unchecked because HLSL specifies out-of-range sample indices as undefined. The scalar DXIL adapter fixture comes from the checked-in compiler output and its D3D12 GPU test clears a 4x-MSAA R32_FLOAT target, reads sample 2 through the common path, and checks the result bits. The array adapter test mutates that real DXIL module's resource kind and third coordinate, checks the layer/sample operands in common IR and MSL, then compiles the emitted MSL with Apple's compiler. This is synthetic adapter coverage; a D3D12 array-resource GPU readback is not yet covered. Integer MSAA loads and Vulkan execution of this operation are not implemented. D3D12 `Shader4ComponentMapping` is normalized into the common descriptor snapshot, and the common D3D12 compute binder applies it with a Metal texture view. Direct DXIL MSL applies the view mapping to texture `Load`, `Sample`, `SampleBias`, `SampleLevel`, and `SampleGrad` results, typed-buffer `TextureLoad` (opcode 66), typed/raw/structured buffer-load vectors, and ordinary texture `Gather`, including force-zero and force-one selectors while preserving zero for out-of-range loads. Gather selects the mapped source component before gathering its four texel values. The runtime skips a dispatch or draw and reports an unsupported-operation diagnostic when a non-identity mapping is bound to a shader that uses `SampleCmp` or `GatherCmp`; comparison reads still need API-specific component handling. The adapter fixtures check eight unsigned loads/stores, seven signed and float loads, a synthetic Y/Z/W result-field mutation, array layers with negative and oversized indices, the MSAA scalar-float load, and ordinary/comparison gather lowering across 2D, array and cube texture forms. The direct-MSL texture-gather, typed-buffer `TextureLoad`, and typed/raw/structured buffer-load fixtures compile with Apple's Metal compiler. Other float texture shapes and integer texture formats remain outside this common slice. See Microsoft's [DXIL `TextureLoad` specification](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#operations-via-external-functions), [DXIL `BufferLoad` and `RawBufferLoad` contracts](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#bufferload), HLSL [`Load`](https://learn.microsoft.com/en-us/windows/desktop/direct3dhlsl/dx-graphics-hlsl-to-load), [`Texture2DMS::Load`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-texture2dms-load), [`Texture2DMSArray::Load`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-texture2dmsarray-load), [`Gather`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-to-gather), [texture component defaults](https://learn.microsoft.com/en-us/windows/desktop/direct3dhlsl/dx-graphics-hlsl-to-type), [`Shader4ComponentMapping`](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_shader_resource_view_desc), and the [Metal Shading Language Specification](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf).

The DXIL common-IR adapter recognizes 32-bit integer and float loads from a single `ByteAddressBuffer` SRV (resource kind 11) through opcode 68 `dx.op.bufferLoad.i32/f32` and opcode 139 `dx.op.rawBufferLoad.i32/f32`. It treats c0 as a byte offset, converts it to a DWORD index with logical `>> 2`, then adds the extracted component lane (0–3) for either opcode before using the shared bounded buffer access chain; each component has its own bounds check and out-of-range component loads produce zero. Opcode 139 currently requires the raw SRV form, an undefined c1, a nonzero four-bit mask, and four-byte alignment. Only fields enabled by the mask are lowered. Opcode 68 lowers extracted result fields 0–3 for the supported 32-bit raw-buffer form; status-field extraction is not supported. Microsoft documents HLSL `Load2`, `Load3`, and `Load4` as returning two, three, and four values from DWORD-aligned byte addresses, respectively, but these synthetic fixtures do not yet validate compiler-generated DXIL for those source operations. Each extracted 32-bit field becomes its own bounded word read. Float fields are read as raw `uint` words and bitcast to `float`, preserving their 32-bit payloads. Synthetic fixtures convert checked-in typed integer and float buffer DXIL to raw-buffer metadata and select each opcode 68 result field, then verify common IR and generated MSL; the normal runtime test checks each lane by Metal readback and uses 4-, 8-, and 12-byte SRV ranges to make the selected y/z/w component individually out of range. Separate opcode 139 fixtures verify common IR, generated MSL, and Metal readbacks for x/y/z/w-only `i32` and `f32` fields. Integer fixtures also select the highest enabled component from the `xy`, `xyz`, and `xyzw` masks; these remain synthetic DXIL cases and do not establish which masks DXC emits for a given HLSL overload. These exercise the translation path but are not compiler-generated `ByteAddressBuffer` DXIL. 16-bit/64-bit overloads, structured-buffer raw operations, and status-field extraction remain unsupported in the common adapter and continue through the direct DXIL path where available. Fixtures use DWORD-aligned addresses; alignment violations are not covered. The adapter rejects opcode 139 for typed-buffer resources, invalid masks, and extracts of masked-out fields. The mapping follows Microsoft's [DXIL `BufferLoad` and `RawBufferLoad` contracts](https://github.com/Microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#bufferload), [`ByteAddressBuffer::Load2`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/byteaddressbuffer-load2), [`ByteAddressBuffer::Load3`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-byteaddressbuffer-load3), [`ByteAddressBuffer::Load4`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-byteaddressbuffer-load4), and the [`ByteAddressBuffer::GetDimensions` byte-length contract](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-byteaddressbuffer-getdimensions).

The common DXIL adapter also lowers opcode 140 `dx.op.rawBufferStore.i32/f32` for a single `RWByteAddressBuffer` UAV (resource kind 11). It divides the byte offset c0 by four to address a word, adds each enabled component lane, and emits one bounded common word store per x, xy, xyz or xyzw prefix mask; float values are bitcast to their 32-bit `uint` payload before storing. Synthetic tests mutate the checked-in typed integer and float buffer DXIL, verify the common IR and MSL, and execute all four prefix masks on Metal with exact readback. Additional readback cases use an 8-byte view over a 16-byte allocation to verify a partially out-of-range vector store and a wholly out-of-range store are dropped. Another case takes the offset from a shader-computed buffer value, verifies the generated MSL uses that value, and reads back the write at the resulting byte offset. Raw SRV and UAV `GetDimensions` queries return the bound view length in bytes by scaling the common uint-word array length by four; synthetic `i32` and `f32` fixtures exercise both descriptor classes with Metal readback. Structured SRV and UAV `GetDimensions` return the view's element count by dividing its byte range by the DXIL metadata stride, for positive strides divisible by four. Synthetic typed-DXIL mutations test stride four and eight with an 8-byte view; SRV cases verify the count through Metal readback, and the stride-four UAV case also reads back its result. The stride-eight UAV-only fixture checks the divisor in common IR/MSL and dispatches after removing its output store, so that particular test does not assert a runtime result. Structured opcode 68 `BufferLoad` supports 32-bit integer or float result fields 0–3 when each four-byte component fits inside the element stride and c1 is a constant, DWORD-aligned byte offset. It computes `elementIndex * (stride / 4) + (byteOffset / 4) + resultField` and uses common buffer bounds so out-of-view loads return zero. Synthetic metadata mutations verify stride-four element loads, a stride-eight member offset and field 1, a combined stride-sixteen byte offset and field 2, an out-of-view element, rejection of a field beyond the stride, and a stride-sixteen float field 3 with bit-preserving Metal readback; these are not compiler-produced structured DXIL. Nonconstant structured byte offsets, status-field extraction, non-32-bit results, general structured stores, and structured raw loads/stores remain unsupported by this adapter. This follows Microsoft's [DXIL resource metadata, `BufferLoad`, and `GetDimensions` specification](https://github.com/Microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst) and HLSL [`StructuredBuffer::GetDimensions`](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/sm5-object-structuredbuffer-getdimensions).

The DXIL common-IR adapter lowers 32-bit `Bfrev`, `Countbits`, `FirstbitLo`, `FirstbitHi`, and `FirstbitSHi` intrinsics (opcodes 30–34) for scalar and 2–4 lane integer vectors. `Ibfe`, `Ubfe`, and `Bfi` (opcodes 51–53) remain scalar-only; the adapter reorders DXIL's width/offset-first arguments into the common bit-field operation order, preserves signed extraction for `Ibfe`, and masks width and offset to their low five bits as required by DXIL. `dxil_bit_intrinsics.metal` checks the scalar bit-field and unary operations, and the adapter test also checks vector result shapes for the five unary operations. The Metal compiler builds the scalar MSL fixture during `make check`. Non-32-bit overloads remain unsupported. The common MSL bit-scan lowering also handles SPIR-V `GLSL.std.450` `FindILsb`, `FindSMsb`, and `FindUMsb` for 32-bit scalar and 2–4 component vector values, including the all-bits-set result for zero (and for signed MSB inputs 0 and -1). It converts `clz` to a bit index with `31 - clz`; a Metal runtime shader test checks ordinary and edge-case values. See Microsoft's [DXIL operation specification](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#operations-via-external-functions) and Khronos's [GLSL extended-instruction specification](https://registry.khronos.org/SPIR-V/specs/unified1/GLSL.std.450.html).

The DXIL adapter also normalizes `dx.op.unary` opcodes 6–29 into common IR: absolute value, saturate, scalar and vector `isnan`/`isinf`/`isfinite`/`isnormal`, trigonometric and hyperbolic functions, base-2 exponential/logarithm, square root/reciprocal square root, fractional part, and the four rounding modes. This slice accepts 32-bit float scalars and 2–4 lane vectors for arithmetic and classification, with scalar or matching bool-vector results. `Round_ne` maps to ties-to-even (`rint` in MSL), while `Round_ni`, `Round_pi`, and `Round_z` map to floor, ceil, and truncation. A synthetic DXIL fixture checks every opcode's common operation and generated MSL; `make check` compiles that MSL. Real typed-buffer fixtures exercise `dx.op.binary` integer opcodes `IMax`, `IMin`, `UMax`, and `UMin` (37–40), preserving signedness from the opcode while lowering signless DXIL `i32` values to typed Metal operations; the D3D12 runtime test dispatches this shader and reads back all four results. A separate 32-bit float fixture covers `FMax` and `FMin` (35–36). Their common-IR flags preserve operand-order selection for ties, return the numeric operand when exactly one operand is NaN, and compare denormals as signed zero while retaining the selected original value. The Metal runtime test checks both signed-zero operand orderings, NaNs on either side, ordinary finite ordering, and positive/negative denorm-versus-signed-zero comparisons. Other overloads and unlisted DXIL operations remain on the direct translator or return unsupported. The mapping follows Microsoft's [DXIL operation specification](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#operations-via-external-functions).

Common MSL comparison lowering preserves per-lane boolean-vector results for 2–4 component numeric comparisons. Ordered and unordered floating comparisons use Metal's component-wise boolean operators (`&` and `|`) for vector results, while scalar results keep scalar logical operators. The DXIL adapter test covers all 14 LLVM floating-comparison predicates on `float2` operands and checks each common-IR operation and bool2 result shape. A synthetic SPIR-V float2 fixture covers the four vector classification operations, `OpOrdered`/`OpUnordered`, and all `OpFOrd*`/`OpFUnord*` forms; the generated MSL compiles with Apple's Metal compiler. These vector checks cover translation and compilation, not GPU execution or result readback.

DXIL `IMad` and `UMad` (tertiary opcodes 48–49) lower scalar and 2–4 lane vector 32-bit integer operands to the shared integer multiply-add operation. The common MSL backend computes vectors through unsigned lanes so overflow wraps modulo 2³² without signed-overflow behavior, then bit-casts results back for signed destinations. A DXC-compiled scalar fixture contains both overloads; the common-IR check verifies opcode signedness and three operands, Metal compiles its MSL, and a D3D12 dispatch reads back overflow cases through typed buffer views. A synthetic DXIL module checks 2-lane signed and 4-lane unsigned overloads in the adapter, and a common-IR fixture compiles signed `int2` and unsigned `uint4` MSL. GPU readback remains verified for scalar overloads; vector forms have translation and compiler coverage only, while other widths remain unsupported.

DXIL `FMad` (tertiary opcode 46) lowers for scalar and 2–4 component 32-bit floats into a distinct common operation from fused `FMA`. The Metal backend stores the product in a volatile intermediate before adding the third operand, then compiles only shaders containing this operation in Metal's safe math mode so the optimizer cannot contract the pair into one fused rounding. A precise DXC fixture retains the `!dx.precise` annotation and produces the cancellation case `((1 + 2^-23) * (1 - 2^-23)) - 1`, which separately rounds to positive zero; a fused operation would produce `-2^-46`. The common IR and MSL are checked, Metal compiles the output, and D3D12 executes and reads back that exact result. Half/double FMad and other denormal modes remain outside this slice. Microsoft's [DXIL operation specification](https://github.com/microsoft/DirectXShaderCompiler/blob/main/docs/DXIL.rst#operations-via-external-functions) distinguishes FMad from Fma and requires non-fused behavior for precise operations; Apple's [MTLMathMode documentation](https://developer.apple.com/documentation/metal/mtlmathmode) documents the safe mode as disabling transformations that alter results.

The DXIL common vertex adapter also lowers scalar `SV_VertexID` and `SV_InstanceID` signature inputs to built-ins. It accepts the DXIL `Invalid` component type and system-generated start rows `0` and `-1`, while rejecting ordinary packed rows. The IR keeps Vulkan's `InstanceIndex` (which begins at Vulkan `firstInstance`) separate from D3D's per-draw zero-based `SV_InstanceID`; D3D's `StartInstanceLocation` separately offsets per-instance vertex-buffer reads. Metal's `instance_id` begins at `baseInstance`, so the D3D path subtracts `[[base_instance]]` before exposing the value to the shader. The fixture checks both built-ins, the `-1` signature row, generated MSL and Metal compilation. These semantics follow Microsoft's [system-generated values](https://learn.microsoft.com/en-us/windows/win32/direct3d11/d3d10-graphics-programming-guide-input-assembler-stage-using), [`DrawInstanced`](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-drawinstanced), the Khronos [`InstanceIndex` definition](https://registry.khronos.org/vulkan/specs/latest/man/html/InstanceIndex.html), and Apple's [Metal draw instance IDs](https://developer.apple.com/documentation/metal/mtlrendercommandencoder/drawprimitives%28type%3Avertexstart%3Avertexcount%3Ainstancecount%3Abaseinstance%3A).
